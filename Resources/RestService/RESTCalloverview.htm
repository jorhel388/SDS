REST Call

The REST Call component can be used in a process node within the following flow(s) to call the external service defined in a Swagger component:

  • Decision Process Flow

The diagram below illustrates at a high level the REST Call process.

Overview

The REST Call component is used to call the external service defined in a Swagger component. It takes the data from the Logical Data Source component and uses it to create the call request and then maps the response back to the component.

The REST Call editor allows the user to define the REST Call component definition. This includes assigning the service provider by selecting:

  • the Swagger component
  • the associated Logical Data Source to use for the input and output data
  • the service to call
 

The Logical Data Model output will contain some common REST API characteristics. For more information, refer to the Common REST API characteristics topic.
 

The connection information and security settings must be configured for the REST Call outbound in the runtime environment. For more information, refer to the following documentation(s):

  • Configuring the REST Call outbound topic in the Business Process Server Configuration Guide
  • Configuring the Decision Agent topic in the Decision Agent Guide

Before the REST Call component can be tested in a flow using the Interactive Tester, users must either configure the scl.cfg file, or associate a Connection Profile to the Swagger component, see the Configuring a REST Call in preparation for testing a flow section below.

Swagger component

The Swagger component links the REST service data contained in a Swagger specification file to a Logical Data Model component.

Swagger is an open-source software framework which is used to describe an API using a human- and machine-readable common language, and is supported by a wide range of third party tools. Swagger is a specification file created and provided by a service or an API provider (for example, Experian, Amazon). This file contains the information that standardises API practices to provide access to the services using REST protocols. This file includes information such as the available entry points (or services) including their URL and authentication, input and output parameters.

The Swagger editor allows the user to attach a Swagger definition file and launch the Swagger wizard or Swagger Update wizard:

  • Swagger wizard - generates the service components for the selected service. The generated service components are linked to the selected service and include a Logical Data Model, a Logical Data Source, and a REST Call.

  • Swagger Update wizard - updates the Logical Data Model structure of services with changes defined in the attached Swagger definition file supplied by their Third-Party provider. These changes may include for example updates in the Data Model, such as newly added characteristics or modification of existing characteristic definitions.

Define a REST Call using the Swagger wizard

The following steps provide instructions on using the Swagger wizard to generate service components and to update the generated REST service components such as when linking the REST Call component to an existing Logical Data Source without affecting the selected Logical Data Source.

Create a Swagger Component
  1. From the Explorer window, right click at the required folder level and select Add component.
  2. Select Swagger.
  3. In the Create component dialog enter the name of the Swagger component.
    4.  

    Only alphanumeric letters (A-Z or a-z), digits (0-9), parentheses (()), space ( ), underscore (_) and dash (-) are allowed in the Swagger component name.
  4. Select the Open new components in component editor checkbox.
  5. Click OK. The Swagger editor will be open allowing you to edit the Swagger. The Swagger component name will be listed in the Explorer window under the selected folder level and is identified by the icon.

If you do not wish the editor to open, keep the check box de-selected. From the Explorer window right click on the Swagger component and select Open.

Define a Swagger component
  1. With the Swagger editor open, click Attach…
    The software opens the Attach dialog from where you can navigate to the file you require.
  2. Select the required Swagger specification file (.json or .yaml format) and click Attach.
    The Attach dialog will close and populate the Swagger editor with the information contained in the attached Swagger specification file.
  3. Within the Name column, double click on the cell and type the name for the service you wish to use.
    4. An invalid Logical Data Model icon appears in the Logical Data Model column.
     

    To remove a service name, right click on the service and select Clear Service Name. The same action is available in the toolbar.

     

    Use the Validation functionality to view information relating to an error.


  4. Optionally, repeat step 3 to define the required services.
  5. Save the changes.
Use the Swagger Wizard to generate the service components

To use the Swagger wizard to generate the service components

  1. Within the Swagger editor, right click on the service name for which you want to generate the associated service components and select Generate service components or select the following icon in the toolbar .
    2.  

    For information on the service details (for example, Index, Path, Method), refer to the Table Columns section in the Swagger editor topic.

    The Swagger wizard will be displayed.

  2. In the Service Components screen, within the Logical Data Model section of the wizard, click on the ellipsis button and select the target folder in the solution to store the Logical Data Model component that will be generated.
  3. The default component name is displayed in the Component field (for example, <service name> LDM). Optionally, type the component name you want to use in the Component field.
      4.  

      Information relating to the configuration can be viewed in the information area below the Component field.
  4. Repeat the above steps to define the Logical Data Source and REST Call components.
      5.  

      From step 1 of the wizard, you can use an existing Logical Data Source component and link it to the REST Call component that will be created. The content of the selected Logical Data Source will not be affected.

      To enable the Define Logical Data Source in REST Call section in the next screen, deselect only the Logical Data Source checkbox.

      In Step 2. Additional Information of the wizard.

      The Logical Data Model content type section allows you to select the content type to generate.

      From the Define Logical Data Source in REST Call section, you can select the folder that contains the existing Logical Data Source using the Browse button. Then select the Logical Data Source that will be linked to the REST Call component from the drop down list in the Component field.

       

      The Component field will be disabled if there is no Logical Data Source in the selected folder.
  5. Click Next.
  6. The Additional Information screen will be displayed and the Logical Data Model Classic content will be selected as the default setting.
    If you wish to generate the Logical Data Model component with JSON content (or with Semi Structured Data Definition content), from the Logical Data Model content type section of the wizard, select the radio button corresponding to the required content type.
      7.  

      The Logical Data Model will be generated with JSON content based on two characteristics, one for the request and the other for the response. These characteristics are stored in a string and share the same name ‘PlainTextJson’. They are in the same Logical Data Model (input and output) but are in different sub-Logical Data Models. An example is shown below.
       

      The next page of the wizard (Step 3. Logical Data Model Content) will only appear, if the content to be generated requires additional user input to complete any missing information.
  7. Click Next.
  8. The Logical Data Model Content screen will be displayed. Click on the characteristic string length or array size (applicable to Classic content only) that you want to edit and type the new value. By default, characteristic string values that are not specified in the attached Swagger specification file will be set to a value of 1 (for example, length and array size). All other characteristic types are set to their maximum value (ready only).
  9. Repeat step 8 until all the required values are set.
  10. Optionally, to edit multiple string values, hold down the Ctrl key and select the required characteristic row(s).

  11. Click on the Edit selected nodes icon in the toolbar. The Edit Property Values dialog appears displaying the editable value(s).

       

      Depending on the selected row(s), the Edit Property Values dialog will display:

      • both editable values, if the selection contains both values which are not greyed out.
      • one editable value, if the selection contains only one value that is not greyed out.
  12. Type the new values in the Length and/or Array Size fields.
  13. Click OK.
  14. Click Next
    15.  

    The Logical Data Model output will contain some common REST API characteristics. For more information, refer to the Common REST API characteristics topic.

  15. The Summary screen will be displayed. This screen includes information such as the components to be generated, details of each component, etc. If required, this information can be copied and pasted into Word or Excel.By default, only characteristic string values (length and array size) that requires user input are highlighted in yellow. Click Finish. The service components will be generated.
    Once the components have been generated successfully the Information dialog appears.
  16. Click OK to close the Information dialog.
  17. Save the Swagger component, this will avoid having errors in the REST Call component.

The generated service components are automatically linked to the REST Call component and appear in the Explorer window, for example, <service name> LDM, <service name> LDS and <service name> REST Call.

The associated Logical Data Model is automatically assigned to the selected service and appears in the Logical Data Model column of the Swagger editor.

 

From the Swagger editor, you can assign a Logical Data Model component to a REST service. To be compatible, the input and output definitions in both the Logical Data Model and REST service must match.

To assign a Logical Data Model component to a REST service, drag and drop the new component from the Resources window onto the current component in the Logical Data Model column cell.
 

To open a Logical Data Model in its editor from the Swagger editor, right click on the row with the Logical Data Model and select Open Logical Data Model.
Use the Swagger wizard to update the REST Service components

The wizard can be used to update the generated REST service components. For example, when linking the REST Call component to an existing Logical Data Source. In this scenario the content of the selected Logical Data Source will not be affected.

To update the REST Service components using the Swagger Wizard

  1. Within the Swagger editor, right click on the service name you want to update and select Generate service components or select the following icon in the toolbar . The Service Components screen of the Swagger wizard is displayed.
    2.  

    By default, if the selected service contains an existing Logical Data Model both the Browse button and the Existing checkbox will be disabled in the Logical Data Model section.
  2. Optionally, to update the current Logical Data Model, select the Logical Data Model checkbox to enable this section.
      3.  

      If the service contains an existing Logical Data Model the Existing check box will be selected by default. Unselecting the Existing check box will activate the Component field allowing you to create a new Logical Data Model.
  3. From the Logical Data Source section, deselect the Logical Data Source checkbox to disable this section.
  4. From the REST Call section:

    1. Click on the Browse button and select the folder that contains the REST Call component.
    2. Click on the Component field and select the REST Call to be updated via the drop down list.

  5. Click Next.
  6. The Additional Information screen is displayed. From the Define Logical Data Source in REST Call section:

    1. Click on the Browse button and select the folder that contains the Logical Data Source component.
    2. Click on the Component field and select the Logical Data Source that will be linked to the REST Call component via the drop down list. The content of the selected Logical Data Source will not be affected.

  7. Click Next.
  8. The Logical Data Model Content screen will be displayed. Optionally, click on a characteristic string length or array size to edit and type the new value.
      9.  

      Dynamic array can be used by setting the array size to a star (*).
  9. Repeat the above step until all the required values are set.
  10. Optionally, to edit multiple string values in one shot, hold down the Ctrl key and select the required characteristic row(s).
  11. Click on the Edit selected nodes icon in the toolbar. The Edit Property Values dialog appears displaying the editable value(s).
      12.  

      Depending on the selected row(s), the Edit Property Values dialog will display:

      • both editable values, if the selection contains both values which are not greyed out.
      • one editable value, if the selection contains only one value that is not greyed out.
  12. Type the new values in the Length and/or Array Size fields.
  13. Click OK.
  14. Click Next.

  15. The Summary screen will be displayed, click Finish.

  16. Click OK to close the Information dialog.

  17. Save the Swagger component, this will avoid having errors in the REST Call component.

The updated service components are automatically linked to the REST Call component.

Use the Swagger Update wizard to update the LDM structure to match the Swagger definition

The Swagger Update wizard can be used to update the Logical Data Model structure of services with changes defined in the attached Swagger definition file supplied by their Third-Party provider. These changes may include updates in the Data Model, such as newly added characteristics or the modification of existing characteristic definitions.

To update your Logical Data Model (LDM) Swagger definition using the Swagger Update wizard

  1. Within the Swagger editor, right click on the LDM and select Update Logical Data Model (or use either the shortcut key (Alt+U), or click the Swagger Update wizard icon in the toolbar).

  2. In the Logical Data Model Content screen of the Swagger Update wizard:

    1. Optionally, click on a characteristic string length or array size to edit and type the new value.

      2.  

      Dynamic array can be used by setting the array size to a star (*).

    2. Repeat the above step until all the required values are set.

    3. Optionally, to edit lengths and/or array sizes for the selected characteristics in a single action, hold down the Ctrl key and select the required characteristic row(s).

    4. Click on the Edit selected nodes icon in the toolbar. The Edit Property Values dialog appears displaying the editable value(s).

      5.  

      Depending on the selected row(s), the Edit Property Values dialog will display:

      • both editable values, if the selection contains both values which are not greyed out.
      • one editable value, if the selection contains only one value that is not greyed out.

    5. Type the new value(s) in the length and/or array size fields.

    6. Click OK.

    7. Click Next.

  3. The Summary screen will be displayed, click Finish.

  4. Click OK to close the Information dialog.

The Logical Data Model Swagger definition is updated to include the latest changes.

Define a REST Call using the REST Call editor

To define a REST Call via the REST Call editor

  1. From the Explorer window, right click at the required folder level and select Add component.
  2. Select REST Call.
  3. Enter the name of the REST Call.
  4. Ensure the Open new components in component editor checkbox is selected.
  5. Click OK. The component appears in the editor. The REST Call name is listed in the Explorer window under the selected folder level and is identified by the icon.
  6. Click on the Swagger Expand (+) button in the Resources window.
  7. Drag and drop the required Swagger component onto the Swagger field in the REST Call editor.
  8. Click on the REST Service field in the REST Call editor and select the required REST service name via the drop down list.
  9. Click on the Logical Data Source Expand (+) button in the Resources window.
  10. Drag and drop the associated Logical Data Source onto the Logical Data Model field.
    11.  

    For the Logical Data Model to be compatible with a REST Call component, their input and output definitions must match.
  11. Save the changes.
Configuring a REST Call in preparation for testing a flow

During the solution deployment process, the Swagger Client Library (SCL) configuration keys are generated into a template file (for example, scl.cfg.update, scl.<alias>.cfg.update). Once the SCL configuration properties file has been deployed successfully, it can be found in the Output files area of the Job Submission Console.

 

When calling a HTTPS service using the REST Call component, a trust store certificate is required in the following:

  • Decision Analytics Server trust store
  • Decision Agent standalone

For further information, refer to the following:

  • Decision Analytics Servers Installation and Configuration Guide
  • Decision Agent Guide

To test a Decision Process Flow that contains a REST Call outbound using the Interactive Tester, users must either configure the scl.cfg file or associate a Connection Profile to the Swagger component. The scl.cfg file or the Connection Profile is used to establish a connection to an external service.

To configure the scl.cfg file for testing a Decision Process Flow
  1. Open the scl.<alias>.cfg.update file in a text editor.
  2. Copy and paste the content of this file into the scl.cfg file located in the etc folder (Studio: \<installation path>\etc).
  3. Depending on the remote service(s) defined in the Swagger file, configure the required properties in the scl.cfg file.
    4. For an example template of the properties file, refer to the Configuring the Decision Agent topic in the Decision Agent Guide.
  4. Save the changes.

The Decision Process Flow can now be tested using the Interactive Tester. For more information, refer to the Test a complete Decision Process Flow topic.

To configure a HTTPS call in the Studio for a Decision Process Flow
  1. Update the scl.cfg file located in the etc folder (Studio: \<installation path>\etc) with the HTTPS URL and use port 443.
    2.  

    The trust store location and password used by the studio are defined in the eda-server.properties file. This file is located in the user directory.

    Any changes made to the eda-server.properties file will require a studio restart for the changes to take effect.
     

    The certificate should be provided or recovered from the calling service website.
  2. Add the certificate into the trust store file using the Java Keytool or KeyStore Explorer.

The Decision Process Flow can now be tested using the Interactive Tester. For more information, refer to the Test a complete Decision Process Flow topic

Associating a connection profile with a Swagger component

A REST component can use the connection profile after it is associated with a Swagger component. This feature introduces a new property in the Swagger component in its properties panel called connection profile.

The connection profile property is optional. If the property is not defined, the REST component will take the parameters from the existing scl.cfg file. This is to support backward compatibility for the existing solution.

The list will display all available individual connection profiles. When the Studio executes the REST component, the individual connection profile will be combined with the global connection profile.

For more information about Connection Profiles, refer to the Server Connection Profiles Overview.
